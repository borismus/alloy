- [ ] Vault watcher never catches up after a dropped connection, so the UI silently goes stale ("sometimes gets stuck not updating results"). Reproduced deterministically: with the backend bounced mid-session, a conversation created while disconnected NEVER appears (5 items before, still 5 after reconnect), while changes made after reconnect work fine — which is why it presents as intermittent. `src/services/api/tauri-fs-http.ts:218` reconnects the socket after 3s and re-registers watchers but never re-reads the vault, so every gap drops events permanently until a manual reload. Mobile hits this constantly (screen lock / app switch kills the socket). Fix: add an `onResync` callback to `useVaultWatcher`, fire it on reconnect AND on debounced `visibilitychange`, and have App re-read summaries/tasks/notes (~320ms measured on a 2216-conversation vault). TRAP: `loadConversationSummaries()` returns `messages: []`, so a wholesale `setConversations` blanks the conversation currently open — and the lazy-load effect is keyed on `conversations.length`, so it won't re-fire to fix it. The resync must MERGE, preserving `messages`/`messagesLoaded` for already-hydrated conversations and only invalidating ones whose `updated` changed. Two supporting bugs in the same file: (1) line 162, if a reconnect fails while another caller waits, the 100ms `setInterval` never clears and its promise never settles, so `watch()` hangs forever and the watcher never registers; (2) iOS leaves half-open sockets reporting `OPEN` with no data flowing, so `onclose` never fires and no reconnect is attempted — resyncing on foreground sidesteps this without needing a heartbeat.

- [ ] Fix camera photos being stored rotated 90°. NOT an iOS bug — the cause is Alloy's own `maybe_downscale_image` in `alloy-server/src/routes/fs.rs`. Phone cameras store portrait shots as *landscape* pixels plus an `EXIF Orientation` tag (the standard behavior); that function calls `image::load_from_memory`, which decodes raw pixels and ignores the tag, then re-encodes via `write_to`, which drops all EXIF — leaving landscape pixels with no correction left. Only triggers above `MAX_IMAGE_DIM` (1568px), which every camera photo exceeds, so smaller images/screenshots keep their EXIF and look fine; this is why it presents as "camera photos are always rotated". Confirmed on `conversations/attachments/2026-08-01-0743-82b6-img-001.jpg`: stored 1568x1176 landscape, 0 EXIF keys, visibly sideways. Because the tag is destroyed at write time, EVERY consumer sees it rotated — the composer thumbnail, the message bubble, and all vision models — so this silently degrades image understanding, not just display. Fix: before resizing, read the orientation (`image::metadata::Orientation::from_exif_chunk`) and bake it into the pixels (`DynamicImage::apply_orientation`); both exist in the pinned image 0.25.10. Note it is a Rust/server fix, so it applies to desktop and mobile alike. Add a test with an orientation-tagged fixture asserting post-write pixel geometry. Existing attachments already lost their EXIF and would need a one-off repair if worth it. While here, delete `src/services/imageUtils.ts`'s `compressImageToFit` + its test — dead code (never called from anywhere) and superseded by this server-side downscaler.
