# Backlog

Tasks for the autonomous backlog runner (`scripts/backlog-runner.sh`).
Each `- [ ]` is one self-contained task. The runner picks the first open one,
works it on an `auto/<slug>` branch, verifies, and opens a PR for review.

Keep tasks small and unambiguous — one PR's worth of work each. Completed work
and the mobile-reliability checklist are archived in
[`docs/backlog-archive.md`](docs/backlog-archive.md).

- [ ] Investigate and fix scrolling that intermittently stops responding on mobile. Reported from real use: scrolling sometimes "just kinda stops" and no reliable repro is known yet, so the first deliverable is a repro or a ruled-out list, not a speculative patch. Suspects to check before changing anything: `useAutoScroll` / `useScrollToMessage` fighting a user-initiated scroll mid-stream; `useWindowedList` windowing in the sidebar leaving the container short and stranding the scroll position; `useLongPress` calling `preventDefault()` on `touchend` and swallowing a touch sequence that was actually a drag; the `position: fixed` + `overscroll-behavior: none` app shell in `App.css` interacting with `-webkit-overflow-scrolling: touch` and `overscroll-behavior: contain` on the messages list in `ChatInterface.css`; and the on-screen keyboard resizing the visual viewport. Determine whether it is WKWebView-only (Tauri iOS) or also reproducible in mobile Safari against web mode — if it is a platform-level WKWebView behavior, say so plainly and document it instead of adding workarounds. Capture which surface it happens on (conversation, sidebar timeline, note) and whether the container has scrolled at all or is merely frozen. Any fix must keep streaming auto-scroll, find-in-conversation jumps, long-press context menus, and sidebar windowing working, and be covered by a smoke test on the seeded mobile browser profile where possible.
- [ ] Make an expired Claude subscription login obvious and recoverable instead of a generic task failure. `claude-cli` turns fail with `Failed to authenticate: OAuth session expired and could not be refreshed`, surfaced as an ordinary turn error: a scheduled task records it as a run failure, emails the first one, and keeps failing on schedule until someone reads the message closely, while an interactive turn shows the raw CLI text with no indication that the fix is a login rather than a retry. It recurs because the subscription session expires on its own, and the durable fix (`claude setup-token`, stored as the provider's `oauthToken`) is interactive and cannot be performed by the failing process. Detect the authentication-expired shape from the `claude-cli` adapter specifically — not by matching "auth" anywhere in arbitrary provider output — and classify it as a distinct failure kind carried on the existing atomic failed-turn record. Surface it as an actionable state rather than a stack of identical errors: say which provider needs signing in again and what to run, link it from the task's failure row, and show it once in Settings next to that provider rather than once per failed run. A scheduled task that fails only for this reason should not keep emailing on every occurrence — reuse the existing first-failure-only behavior keyed on the classification. Do not attempt an automatic re-login, do not silently fall back to another provider or model, and never log or persist token values. Cover the classifier against real expired-session output and against unrelated CLI errors that must stay generic, the persisted failure kind, the Settings/task surfaces, and the email suppression.
- [ ] Preserve bounded provider-supplied reasoning when a conversation turn fails. `SessionInner.full_thinking` already retains up to 128 KiB for live replay, but `mark_error()` clears it and `AssistantWrite` has no reasoning field, so a long failed run can leave an empty assistant record even when the provider streamed useful working notes. On the existing atomic failed assistant record only, persist that buffer in a clearly named optional field, render it as collapsed **Incomplete model reasoning**, and include a labeled section in the generated Markdown preview for posterity. Never invent reasoning for providers that do not supply it, persist it for successful turns or metadata logs, or feed it back into later model context. Preserve the existing bound and truncation marker. Treat this as diagnostic salvage, not as a final answer or a substitute for preventing failure. Cover failures before and after visible content, reconnect/reload, Markdown generation, absent reasoning, truncation, and secret-canary exclusion from logs.
- [ ] Implement manual conversation compaction end to end, then restore the **Compact now** action in the context-usage popover. Add an authenticated backend route that compacts the selected persisted conversation using the existing server-owned compaction/model-selection machinery, writes the compacted boundary atomically without dropping attachments, tool history, newer turns, or concurrent optimistic user messages, and returns the updated conversation. Reuse the automatic-compaction format and provider-native one-shot model behavior rather than creating a second summary schema. The client action must show progress, reload the resulting conversation, preserve scroll sensibly, and surface failures without leaving a false compacted state. Keep automatic compaction unchanged and cover Tauri and browser/server modes with Rust route/persistence tests and a frontend interaction test. Do not expose a placeholder button before the backend path works.

## Deferred (not scheduled — no `- [ ]`, so the runner skips it)

- **Show exact build identity if stale-build debugging becomes costly again.** Settings and startup logs already show the app version, while the shipped `SharedPortInUse` startup screen makes competing instances explicit and actionable. Development builds still share the same package version, so a future diagnostic could add the compile-time git commit and build timestamp to Settings and startup logs. Do this only if identifying a stale binary remains a recurring problem; the port-conflict portion is complete.
- **Optimize per-token Markdown rendering only after a measured regression.** `MarkdownContent` is currently re-parsed as streaming state changes, but the previously measured 284 ms typing stall came from the now-windowed 1,302-row sidebar, and current conversation responsiveness is acceptable. Do not optimize based on the old measurement. If streaming in a long Markdown/math/code conversation becomes observably slow, first profile render/parse counts, then isolate the active streaming row and memoize completed message bodies while preserving tool pills, wiki links, math, syntax highlighting, find-in-conversation, and auto-scroll. Do not virtualize the message list because browser find relies on its DOM.
