# Backlog

Tasks for the autonomous backlog runner (`scripts/backlog-runner.sh`).
Each `- [ ]` is one self-contained task. The runner picks the first open one,
works it on an `auto/<slug>` branch, verifies, and opens a PR for review.

Keep tasks small and unambiguous — one PR's worth of work each. Completed work
and the mobile-reliability checklist are archived in
[`docs/backlog-archive.md`](docs/backlog-archive.md).

<!-- Tier 1: responsiveness. Measured regressions that affect every interaction. -->
- [ ] Stop re-rendering and re-parsing every message on each streamed token. `MarkdownContent` in [src/components/MarkdownContent.tsx](src/components/MarkdownContent.tsx) is an unmemoized function component running the full remark/rehype/KaTeX/highlight pipeline, and `renderedMessages` in [src/components/ChatInterface.tsx](src/components/ChatInterface.tsx) lists `streamingContent` in its dependency array — so every token rebuilds the entire message list and re-parses the markdown of every prior message. `StreamingContext` additionally bumps a version counter on each token to force consumer re-renders. Memoize rendered message bodies by content identity so completed messages are parsed once, and keep the streaming message the only thing re-rendering per token. Also remove the `[perf]` `console.debug` calls left in the render path. Verify with a streaming turn in a long conversation that per-token cost stays flat as the conversation grows, and that tool pills, wiki links, math, code highlighting, and find-in-conversation still work.

<!-- Tier 2: turns that silently produce wrong or truncated output. -->
- [ ] Never return a truncated stream as a finished answer. In [alloy-server/src/providers/openai_compatible.rs](alloy-server/src/providers/openai_compatible.rs) the SSE loop treats a stream error as `tracing::warn!` + `continue`; the stream then ends, no `finish_reason` is ever received, and `stop_reason` keeps its initial `"end_turn"` value, so the partial text is returned as `Ok(StreamResult { .. })` and persisted as a completed turn. The client is built with a 180 s total `reqwest` timeout that covers the streaming body, so any generation longer than that is silently cut off mid-sentence — and a local 30B model on a large prompt can exceed it (a raw endpoint probe took 434 s for a single call). Distinguish a stream that ended because the model finished from one that ended because the transport failed, and fail the latter through the existing error path instead of persisting it as an answer. The per-call deadline must also become generous and configurable rather than a fixed 180 s; key that off execution mode, not off whether the model is local (see the task-mode execution policy item below). Cover with a provider test that ends a stream mid-body and asserts the turn errors rather than returning partial content.
- [ ] Read the context window advertised by OpenAI-compatible servers. `OpenAIModelEntry` in [alloy-server/src/routes/models.rs](alloy-server/src/routes/models.rs) only deserializes `context_length` (OpenRouter's field name), but oMLX reports `max_model_len` — 131072 for `Muse-Glimmer-30B-4bit`, 262144 for the Qwen models. Every mlx model therefore has `context_window: None`, so `effective_budget`'s `0.6 × context_window` clamp never applies and the context-usage chip has nothing to show for local models. Accept the common aliases (`max_model_len`, `max_context_length`, `context_window`) alongside `context_length`, keep `None` when a server advertises nothing, and cover the parsing with a unit test per alias. Prerequisite for giving a turn a real context budget.
- [ ] Give a single turn a context budget. [alloy-server/src/compaction.rs](alloy-server/src/compaction.rs) runs once *before* the tool loop, on conversation history; inside `execute_with_tools` the loop appends assistant tool calls and tool results with no budget at all, so one turn can grow without limit. Observed in production: 278,254 and 314,102 cumulative input tokens, turns of 939 s and 503 s, and 16 `search_directory` calls in a single turn several of which repeated an earlier query verbatim. The existing limits are the wrong shape for this — `MAX_ITERATIONS` caps rounds, `MAX_WEB_SEARCHES` caps searches, and per-result caps bound one result (`MAX_BODY_BYTES` 2 MB, `MAX_READ_BYTES` 64 KB), but nothing bounds the accumulated total. Prefer eliminating waste over discarding evidence, because these turns are run for accuracy and dropping a tool result can remove exactly the fact the answer needed. Start with the lossless wins: short-circuit a repeated identical tool call with its previous result instead of re-running it, and stop re-reading a file already read this turn. Only if a turn still exceeds a budget derived from the model's context window should it compact older tool results — summarizing rather than deleting, and never touching the user message or the assistant's own narration. Track the running total with `compaction::estimate_tokens`. Prove the win by replaying a large turn and recording tokens and wall-clock before/after; correctness bar is that a turn which fits comfortably today behaves identically.
- [ ] Stop truncating a turn when the tool loop hits its iteration cap. `execute_with_tools` in [alloy-server/src/tool_loop.rs](alloy-server/src/tool_loop.rs) caps a turn at `MAX_ITERATIONS` (10) and then breaks silently. The forced tool-free wrap-up that would produce a real conclusion only runs when `final_content.trim().is_empty()`, so a model that narrates while it works — which most do — gets its running commentary saved as the final answer, cut off mid-plan, with no indication anything was truncated. Observed with `mlx/Qwen3.8-27B-MLX-4bit` in a turn that ran 27 tool calls and ended on "Several strong candidates. Reading the most promising ones now." and was stored as an ordinary successful turn. When the loop exits because the cap was reached rather than because the model stopped asking for tools, run the same wrap-up call (tools withheld plus the existing `WRAP_UP_INSTRUCTION`) and append its answer to the narration instead of discarding it; if that call still yields nothing usable, fail the turn through the existing error path rather than persisting a mid-sentence answer. A turn that ended on its own must be completely unaffected — no extra provider call. Note that the iteration cap is only one of two ways a turn ends mid-thought — a silently truncated stream (see the item above) produces an identical-looking result, and the two cannot be told apart from the stored conversation alone, so land the logging item before concluding which one a given report was. Also revisit whether `MAX_ITERATIONS = 10` is the right ceiling for accuracy-first scheduled runs, where finishing the research matters more than finishing quickly; consider a higher or per-task limit rather than assuming 10. Cover with tool-loop tests for cap-with-narration, cap-with-blank-content, and natural completion.
- [ ] Give task execution its own turn limits, separate from interactive chat. Scheduled runs go through `tasks::executor::run` and inherit every interactive default — 180 s per call, `MAX_ITERATIONS = 10`, `MAX_WEB_SEARCHES = 3`, 8192 output tokens — even though a cron run is explicitly not time-sensitive and is expected to favour finishing the work over finishing quickly. Introduce an execution policy carried on `StartParams` next to `retry_connect` and marked `#[serde(skip)]` for the same reason: an HTTP client must not be able to grant itself longer deadlines or more iterations, and the executor sets it after construction. Key the policy on **execution mode, not on whether the model is local** — `model_is_local` is a trust signal that gates `privateReadOnlyDirs` access and must not acquire performance semantics, and a cloud model on cron is equally free of a waiting user. Because `Run now` (`/api/tasks/{id}/run` → `scheduler::run_by_id`) shares the executor path, manual runs get the same policy automatically, which is the intent. Ship sensible task defaults (a much longer per-call deadline and a higher iteration ceiling), allow global overrides under a `taskExecution:` block in config.yaml, and allow a per-task override in the task YAML for the occasional job that should stay short. One implementation wrinkle: the timeout is currently baked into the `reqwest::Client` built in `OpenAiCompatibleProvider::new`, so a per-turn deadline needs `RequestBuilder::timeout()` per request rather than one client-wide setting. Interactive chat behaviour must be byte-for-byte unchanged. Mirror the existing `interactive_clients_cannot_enable_task_connection_retries` test for the new policy, and cover that cron and Run now resolve to identical limits.

<!-- Tier 3: diagnosability, then feature work. -->
- [ ] Log enough to explain a turn after the fact, and keep the logs. `init_logging` in [src-tauri/src/lib.rs](src-tauri/src/lib.rs) writes only to stderr, which is discarded when the app is launched from Finder — so a production failure leaves no diagnostic anywhere. Add a rotating log file in the platform log directory (`~/Library/Logs/Alloy` on macOS) alongside stderr, keeping the `ALLOY_LOG` override and a small retention cap, and share one initializer between the Tauri shell and `alloy-serve`. Then log what actually explains a turn: model and provider, message count, each tool-loop iteration's stop reason, tool-call count and names, whether the forced wrap-up fired and why, final content length, token usage, and duration. **Log metadata only — never message text, tool results, prompts, note contents, or credentials**, since these files sit unencrypted next to a private vault; where output shape matters, log a classification (for example “final content looks like unparsed tool-call markup”) rather than the text. A recent investigation could not determine whether malformed output came from a loop round or the wrap-up because neither is logged at any level.
- [ ] Make it obvious which build is running. Debugging twice reached the wrong conclusion because a stale Tauri dev binary kept serving old code: `npm run tauri dev` only rebuilds Rust at process start, and the dev log showed repeated `0.0.0.0:3041 is already in use` from competing Alloy instances whose output went to different places. Surface the running build — version, git commit, and build timestamp — in Settings and in a startup log line, sourced at compile time so it cannot drift. In dev, make a port conflict impossible to miss rather than falling back silently to another port while an older instance keeps serving the UI. Cover the version/commit plumbing with a test and check the conflict path in both Tauri and standalone modes.
- [ ] Protect `memory.md` from a destructive model rewrite. It is the one file injected into every system prompt, so damage there silently degrades every future turn in every conversation, and it is hand-curated (41 lines: 5 headings, 22 bullets) so it cannot be reconstructed from anything. `skills/save-memory/SKILL.md` instructs the model to `write_file` the **complete** updated content, and `execute_write` in [alloy-server/src/tools/files.rs](alloy-server/src/tools/files.rs) is a plain `fs::write` truncating overwrite — so a model that summarizes carelessly or truncates mid-generation (which the local models here demonstrably do) replaces curated memory with less than it had. There is no git history in the vault, no backup file, and no diff shown; the file was last written 2026-08-25, so a silent loss could go unnoticed for months. This is specifically about `memory.md` rather than writes in general — `notes/` is intentionally writable without approval and should stay that way. Before overwriting `memory.md`, keep a timestamped copy under a small capped backup location, and treat a write that removes a large fraction of the existing content as suspect: either refuse it with an explanatory tool error the model can react to, or require the caller to re-read the file first. Surface what changed rather than writing silently. Cover with tool tests for a normal append-style update, a truncating rewrite, and backup rotation.
- [ ] Wrap long unbreakable titles in the sidebar timeline. `.item-preview` in [src/components/Sidebar.css](src/components/Sidebar.css) sets no `overflow-wrap`, so a conversation titled with a bare URL (the fallback title is the first message) runs past the card's right edge and is visually clipped, while the remainder wraps to the next line — e.g. `https://www.collisiondetector.com/front` + `the`. The sibling `.item-search-snippet` already handles this with `overflow-wrap: anywhere`. Apply equivalent breaking to the title while keeping its existing two-line clamp, ellipsis, and the right padding that leaves room for the actions button. Check a long URL, a long unspaced word, and ordinary prose titles at both desktop and mobile sidebar widths.
- [ ] Add native PDF attachments to conversations. Generalize the current image-only `Attachment`, pending-composer, queue, vault-storage, and server message types to support `document` attachments while preserving every existing image path. Accept `application/pdf` from the file picker and drag-and-drop, store the original PDF under `conversations/attachments`, and render an accessible filename chip before and after sending. Add a provider/model `supportsDocuments` capability and send PDFs only through verified native document protocols (initially Claude subscription and OpenRouter); unsupported providers such as Codex app-server and oMLX must block the attachment with a clear explanation rather than silently dropping it or uploading it elsewhere. Respect each upstream size/page limit, keep vault paths private, and never fall back from a local provider to cloud. Cover Tauri and browser/server modes with unit tests for capability gating and wire shapes plus a smoke test using a real small PDF.
- [ ] Implement manual conversation compaction end to end, then restore the **Compact now** action in the context-usage popover. Add an authenticated backend route that compacts the selected persisted conversation using the existing server-owned compaction/model-selection machinery, writes the compacted boundary atomically without dropping attachments, tool history, newer turns, or concurrent optimistic user messages, and returns the updated conversation. Reuse the automatic-compaction format and provider-native one-shot model behavior rather than creating a second summary schema. The client action must show progress, reload the resulting conversation, preserve scroll sensibly, and surface failures without leaving a false compacted state. Keep automatic compaction unchanged and cover Tauri and browser/server modes with Rust route/persistence tests and a frontend interaction test. Do not expose a placeholder button before the backend path works.
